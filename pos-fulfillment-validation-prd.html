Overview

In-POS Fulfillment Validation brings package scanning and confirmation into the SellTreez POS so budtenders never have to leave their screen to complete a sale. When enabled, a sale cannot proceed to checkout until the items on the order have been physically scanned and verified at the register — either by the budtender themselves or as a second confirmation after back-of-house fulfillment processing.

The feature introduces two new POS actions: Send to Fulfillment, which saves the ticket, surfaces the order in the fulfillment dashboard, and optionally prints a packing receipt at POS; and Fulfill & Checkout, which opens a scan verification modal at the register before completing the sale. Together these replace the current two-tab workflow and ensure checkout cannot occur without physical product confirmation at the register.

This flow is familiar to operators converting from Dutchie's swimlane model and is designed specifically for lean and multi-role store operations across Illinois, New Jersey, New York, and Ohio.

Problem

Stores operating without a dedicated or reliable fulfillment team face a persistent verification gap in the current POS workflow:

  • Budtenders can add items manually via the + button and check out without ever scanning a single item — there is no enforcement that physical product was confirmed when the fulfillment dashboard is not part of the workflow.
  • The two-tab workflow (build in POS → validate in fulfillment tab) is a hard training shift for operators migrating from Dutchie who are accustomed to swimlane-based fulfillment.
  • Fulfillment status is not visible in the open POS ticket — there is no in-context signal while an order is being edited.
Key bypass gap
Budtenders can build an order entirely with the + button and check out without any physical product confirmation. The new flow closes this gap: printing a packing receipt and proceeding to checkout both require going through the Send to Fulfillment and scan verification steps.

Goals

  • Budtenders complete the full sale — including physical product confirmation — without switching tabs or screens.
  • Checkout is hard-blocked until every item has been scanned at POS, with no bypass outside of a logged manager override.
  • The feature supports three distinct operational models (see Supported Flows) through two config modes (Always and Fallback) applied independently per order type.
  • Existing fulfillment infrastructure is reused throughout — FIFO package assignment, package mismatch config, packing receipt format, printer routing, fulfillment dashboard ticket surfacing, and existing block/revert configs — rather than rebuilt. Packing receipt printing from POS is net-new but reuses the existing format and printer routing config.

Non-Goals

  • Does not replace the fulfillment dashboard for BOH-only workflows.
  • Does not change FIFO package assignment logic.
  • Does not introduce a new receipt format.

Scope

In Scope — MVP

  • "Send to Fulfillment" button with 3-option confirmation modal
  • "Fulfill & Checkout" button opening scan verification modal
  • Scan modal: per-item verification states, All/Scanned/Waiting filter with counts
  • Per-unit barcode scanning (one scan per unit)
  • Wrong product prompt + one-scan add and auto-verify
  • Package mismatch handling (reuse existing config)
  • Cart row visual distinction (pending / verified / needs scan)
  • Always mode: full rescan of all items at every checkout attempt
  • Fallback mode: reuses existing Packed & Ready block + revert-on-edit configs
  • Config per order type (6 types × Off / Always / Fallback); default Off
  • Manager override (PIN, logged)
  • Optional packing receipt print from POS on "Send to Fulfillment" (net-new; reuses existing format + routing)
  • Full receipt reprint on re-send (when print option is selected)
  • Fulfillment status surfaced in open POS ticket

Out of Scope — Fast Follow

  • Delta packing receipt (only new/changed items reprinted)
  • Automated order routing to specific printers beyond existing config

Supported Fulfillment Flows

Three distinct operational models are supported. All use the same POS mechanics — they differ in who picks product and whether the fulfillment dashboard is involved.

Flow 1 — Budtender Picks (No Fulfillment Team)

Config: Always. No BOH involvement. Budtender is responsible for building, picking, and verifying the order entirely.

4

Scan verification modal opens. Budtender scans all items. Every unit must be scanned fresh — no carry-over from prior sessions.

All items verified — checkout completes normally.

Flow 2 — BOH Picks, Cashier Verifies (Lean Fulfillment Team)

Config: Fallback. BOH normally processes orders. If an order is Packed & Ready, checkout proceeds without POS scan. If not, cashier must scan before checkout.

Cashier builds the order with the customer.
2
Tap "Send to Fulfillment"

4

Order is Packed & Ready — existing block config is satisfied. Checkout button shows as "Checkout" (no POS scan required). If order was not processed by BOH, button shows "Fulfill & Checkout" — scan modal opens and pre-validates any items FF already confirmed, so cashier only scans items FF has not yet processed.

Flow 3 — Double Validation (BOH + Cashier Both Scan)

Config: Always. BOH processes through the fulfillment dashboard AND cashier rescans at POS right before checkout. Both are required independently.

Same as Flow 2 — ticket saved, packing receipt sent, fulfillment dashboard ticket created.
2

3

Scan modal opens regardless of Packed & Ready status. Cashier rescans all items as a final confirmation. Always mode does not check FF status.
4
Checkout
All items scanned — checkout completes.

Functional Requirements

"Send to Fulfillment" Button

  • Visible in the POS bottom bar when the feature config is enabled (Always or Fallback) for the active order type.
  • Disabled when the cart has zero items; enabled when the cart has at least one item.
  • Tapping opens a confirmation modal with:
    • A "Print packing receipt" checkbox — checked by default. Allows budtender-picks stores to print at POS; BOH-heavy stores can uncheck since their receipt comes from FF dashboard auto-print.
    • Cancel — dismisses modal, no action taken.
    • Send & Stay on Sale — saves the ticket, surfaces order in FF dashboard, optionally prints packing receipt, remains on the active sale screen.
    • Send & Exit Sale — same as above, then exits the sale session.
  • On confirmation, the ticket is saved and surfaces on the fulfillment dashboard. The fulfillment status pill on the open ticket updates to Awaiting Processing.
  • Does not open a scan modal — scanning happens separately at checkout via "Fulfill & Checkout."
  • Can be tapped again after new items are added. Re-tapping presents the same modal — if the budtender checks "Print packing receipt," the full updated receipt is reprinted. The FF dashboard order is always updated with new items regardless of whether a receipt is printed.
  • The "Print Receipt" (customer receipt) button remains disabled until checkout is complete — it cannot be triggered from the POS bottom bar at any point before checkout.

"Fulfill & Checkout" Button

  • Replaces the standard "Checkout" button label when the feature config is enabled and a POS scan is required.
  • In Always mode: always labeled "Fulfill & Checkout." Tapping opens the scan verification modal every time, regardless of fulfillment dashboard status.
  • In Fallback mode: labeled "Checkout" when the order is Packed & Ready (no scan required); labeled "Fulfill & Checkout" when it is not (scan required before checkout).
  • Tapping "Fulfill & Checkout" opens the scan verification modal. The modal presents all current cart items as pending — state is always fresh at the start of each checkout attempt.
  • Once all items in the modal are verified, the modal offers a "Verified — Checkout" action that completes the sale.

Scan Verification Modal

  • Opens when Checkout is tapped and scanning is required. It is a centered overlay — not a full-screen mode change. The cart remains editable while the modal is open.
  • Displays a progress bar (items verified / total) and filter tabs: All / Scanned / Waiting, each with a live item count.
  • Each line shows: product name, package number, quantity, and a validation state indicator (pending circle → checkmark on scan).
  • For qty > 1 lines: each unit requires a separate scan. Progress shown inline ("X of Y scanned").
  • Closing the modal (X button) preserves all scan progress for the session. Items already verified remain verified when the modal is reopened. Scan state resets only if items are added or quantities change on the order.
  • Persistence implementation: The POS payment screen is a Redux tab toggle (paymentTabShowing), not a separate page or route — navigating to payment and back does not destroy the Redux store. Scan state is stored in Redux keyed by ticket ID. sessionStorage keyed by ticket ID serves as a lightweight fallback for edge cases (browser refresh, device switch). No new DB column or API endpoint is required for MVP.
  • "Manager Override" link available for incomplete validation — see Manager Override.

Scan Barcode Type — Design Constraint

The scan verification modal accepts any barcode input and marks the item as verified on a match. The system does not distinguish between a product SKU barcode and a package/lot label barcode. This is consistent with the existing fulfillment dashboard scan behavior, which also does not enforce barcode type.

This means verification confirms "a barcode matching this product was scanned" — not "the exact FIFO-assigned package is physically in hand." This is a known limitation of the current scanning infrastructure, not a gap introduced by this feature.

Scan-to-add is not treated as verification. The existing POS supports scanning a barcode to add a product to the cart. This action cannot be credited as a verification scan — the intent is different (add vs. confirm), and there is no reliable signal that the physical package was present rather than a shelf tag or display item. Verification always happens explicitly in the scan modal. POS scan progress is not reflected on cart rows — the cart only surfaces what fulfillment has confirmed via FF-confirmed status.

Cart Row Visual States

StateConditionVisual Treatment
No badge Ticket not yet saved, or FF has not yet confirmed this item No border accent; no badge
✓ Verified by fulfillment FF has confirmed this item (fulfilledQuantity = quantity) Green left border (#8BC34A); "✓ Verified by fulfillment" badge below product name

There are no invented intermediate states ("Awaiting Scan," "Needs Scan"). The badge appears only when FF has positively confirmed an item. Everything else shows no badge.

POS scan progress is not reflected on cart rows. Scan state from the verification modal lives exclusively in the modal (persisted in Redux for the session). The cart only surfaces what the fulfillment team has confirmed. Showing a POS scan badge alongside FF-confirmed status would imply a level of certainty the system does not have — the scan modal accepts any matching barcode without distinguishing product SKU from package label. Cart rows are not updated mid-session based on modal scan activity. Qty controls and the trash icon remain enabled at all times — the cart is never locked.

Fulfillment Status in Open Ticket

Fulfillment status is currently only visible in the saved sale view. This feature requires it to be surfaced in the active open ticket (edit mode) as a status pill alongside the receipt number at all times — including before the ticket is saved. This is a net-new UI change and a prerequisite for Fallback mode.

Two Config Modes

The feature introduces two validation modes plus Off. Modes are set independently per order type.

No No fulfillment team (budtender picks and scans themselves) or always scan twice (BOH processes AND cashier rescans). Always mode serves two distinct use cases
"No fulfillment team" and "always scan twice" both use the Always config. The system enforces the same behavior for both — a fresh POS scan at every checkout. The operator's operational workflow determines which use case applies; the system does not distinguish between them.
Fallback mode — existing config reuse
Fallback mode reuses two existing configs: (1) "Block checkout until Packed & Ready" — the enforcement gate; (2) "Revert edited order from Packed & Ready to In Process when a new item is added" — ensures BOH must re-process the updated order. No new config keys are required for Fallback. The new POS validation flow is wired as the resolution path when the block fires.

All affected operators support multiple order types. Configuration is set independently per order type to prevent unintended checkout blocks on order types where POS scanning is not appropriate (e.g., delivery). All order types default to Off on initial feature enablement.

Package Mismatch Config

Reuses the existing fulfillment package mismatch configuration — no new config needed:

  • Auto-update: When a different package of the same product is scanned, the order automatically updates to use the scanned package and the line is marked verified.
  • Confirm before update: A prompt shows the original and scanned package numbers and requires confirmation before updating.

Scanning Logic

FIFO & Package Assignment

When a product is added to the cart (via + button or scan in Build mode), FIFO assigns the oldest eligible package to that line. The packing receipt may print without a lot number if FIFO assignment happens at pick time — this is expected. Validation in the scan modal matches against the specific FIFO-assigned package on the order, not just the product SKU.

Scan Outcomes in Verification Modal

Scan resultSystem behavior
Correct product, correct package, units remaining Unit marked as scanned. Progress updates ("X of Y scanned"). When all units for the line are scanned, line moves to Verified.
Correct product, correct package, line already fully verified No action. Scan acknowledged but does not duplicate verification.
Correct product, different package (FIFO mismatch) Triggers package mismatch handling per existing config — auto-update or confirmation prompt before updating.
Product not on the order Prompt: "This product is not on the order. Would you like to add it?" If confirmed, product is added and auto-verified in one action — no second scan required.
Qty > 1 on a line Each unit requires a separate scan — same as existing fulfillment processing behavior.

Modifying Lines During Verification

  • Reduce quantity: Reduces the required scan count. Already-scanned units in excess of the new qty are discarded.
  • Remove line: Line and any associated scans are discarded. No longer counted toward verification requirement.
  • Partial fulfillment: If a product is unavailable, budtender reduces qty or removes the line, then verifies remaining items. No special partial-fulfillment mode needed.

New Items Added After Send to Fulfillment

When a new item is added via the + button after "Send to Fulfillment" has already been tapped, behavior differs by config mode.

Always Mode

The new item appears in the cart with a "Needs scan" badge. Because Always mode always rescans all items fresh at checkout, the new item requires no special handling — it is simply part of the full rescan when "Fulfill & Checkout" is tapped. Re-tapping "Send to Fulfillment" updates the packing receipt so BOH (if present) knows about the new item.

Fallback Mode

Two existing configs handle the happy path:

  1. Adding a new item to a Packed & Ready order triggers the existing "Revert to In Process on edit" config — the order status reverts to In Process in the fulfillment dashboard.
  2. BOH sees the order needs attention, processes the new item, and marks it Packed & Ready again.
  3. Once Packed & Ready, the existing "Block checkout until Packed & Ready" config is satisfied — checkout unblocks with no POS scan required.

If BOH does not re-process the order, it remains In Process (not Packed & Ready) and the Fallback block fires — the scan modal opens at POS. In this case, POS reads fulfilledQuantity per ticket line from the server to pre-populate the modal with what FF already verified, so the cashier only scans items FF has not yet confirmed.

Per-Line Pre-Validation from FF

The existing posper_ticketline.fulfilled_quantity field records how many units of each line FF has processed. It is written only when an order transitions from In Process to Packed & Ready — at that point every line is set to its full ordered quantity. It is not written per-scan; FF scan progress between status transitions is not persisted to the database.

This means fulfilledQuantity is a reliable signal only for lines that have been through at least one PACKED_READY transition:

  • Order was previously Packed & Ready, then pushed back (most common new-item scenario): original lines retain fulfilledQuantity = ordered quantity from the last PACKED_READY. POS shows these as pre-validated. Only the newly added line, which has fulfilledQuantity = 0, requires scanning.
  • Order was never Packed & Ready (still Awaiting Processing or In Process): all lines have fulfilledQuantity = 0. POS cannot distinguish FF progress — cashier scans everything.

POS does not need to write scan results back to the FF dashboard. Once the cashier completes POS validation and the sale is checked out, the ticket moves to Completed — no residual per-line scan state is needed in FF.

What "pre-validated" means in the scan modal
When the Fallback block fires and the scan modal opens, lines where fulfilledQuantity ≥ quantity appear already checked off — the cashier does not need to rescan them. Lines where fulfilledQuantity = 0 are shown as pending and must be scanned. The cashier can see at a glance which item(s) need attention without rescanning everything FF already processed.

Packing Receipt

Net-New Capability: Printing from POS

Today, packing receipts can only be printed from the fulfillment dashboard. This feature introduces the ability to print a packing receipt directly from the POS — required for the budtender-picks flow (no FF team) where the printed receipt is the primary pick list for the back of house.

For BOH flows (lean team, always scan twice), the packing receipt is supplementary. BOH always consults the live FF dashboard order before processing — the screen is the authoritative source. A new item added after the original receipt prints is visible to BOH when they open the order. The receipt gap in BOH flows is therefore lower risk than it initially appears.

Print Option in "Send to Fulfillment" Modal

The "Send to Fulfillment" confirmation modal includes a "Print packing receipt" checkbox. This allows each store type to control print behavior:

  • Budtender-picks stores: Leave checked by default — the receipt is their pick list.
  • BOH-heavy stores: Can leave unchecked — their packing receipt comes from the FF dashboard auto-print.

The checkbox state is not persisted between sends — it defaults to checked on every open of the modal.

Re-send and New Items

Re-tapping "Send to Fulfillment" after new items are added presents the same modal. If the budtender checks "Print packing receipt," the full updated order is reprinted. For budtender-picks flows this is the correct resolution — reprint and re-pick. For BOH flows, BOH sees the updated item on screen regardless of whether a receipt is reprinted.

Delta receipt (new items only) remains a fast-follow. The operational need is lower than initially scoped because BOH flows do not depend on the printed receipt as an authoritative source.

FF Dashboard Badge Gap

When a new item is added to an In Process or Awaiting Processing order, BOH can see the new item on screen but has no visual indicator distinguishing it from original items (the badge only appears on revert from Packed & Ready). This is a FF dashboard gap, adjacent to this feature but out of scope — flagged for the FF team as a follow-up.

Format & Routing

  • Format: Reuses the existing fulfillment dashboard packing receipt — no new template.
  • Printer routing: Routes to any hardware location configurable in the fulfillment dashboard — no new printer config.
  • Reprint: Budtenders can reprint from an open saved ticket without re-triggering "Send to Fulfillment" and without affecting verification state.

Manager Override

  • Available via a "Manager Override" link in the scan verification modal when items remain unverified.
  • Requires entry of a manager PIN.
  • On successful PIN entry, checkout proceeds immediately — scan requirement is bypassed for this transaction.
  • Override is logged with: manager identity, timestamp, ticket ID, count of unverified items, and product names of unverified lines.
  • Override log is accessible to org admins.
  • A persistent indicator on the completed sale record marks that verification was overridden.

Non-Functional Requirements

  • Scan latency: Scan-to-verification-response must feel instantaneous — target under 300ms from scan input to visual state update in the modal.
  • Offline resilience: If scanner input fails or a product has no barcode, a fallback path must exist — manager override is the minimum acceptable path; a per-line manual "mark as verified" with manager permission is preferred.
  • Audit trail: All manager overrides are logged and retained with the ticket record.
  • Config changes: Changing the validation mode for an order type takes effect on the next new sale. In-progress tickets retain the mode active when the sale was started.
  • No data loss: Opening or closing the scan modal, or re-sending to fulfillment, must not affect ticket line data — products, quantities, prices, discounts, and package assignments are preserved throughout.
