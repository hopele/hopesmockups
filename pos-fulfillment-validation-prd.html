Overview

In-POS Fulfillment Validation brings package scanning and confirmation into the SellTreez POS so budtenders never have to leave their screen to complete a sale. When enabled, a sale cannot proceed to checkout until the items on the order have been physically scanned and verified at the register — either by the budtender themselves or as a second confirmation after back-of-house fulfillment processing.

Saving the order is how the fulfillment team is notified — saved orders surface on the FF dashboard automatically, and auto-print config on the FF side determines whether a packing receipt prints in the back. The POS bottom bar provides Save & Exit and Save & Stay actions in place of the old "Save Sale" button. When Checkout is tapped and scanning is required, a scan verification modal opens as a centered overlay — the cart is never locked. Once all items are verified, checkout completes normally.

This flow is familiar to operators converting from Dutchie's swimlane model and is designed specifically for lean and multi-role store operations across Illinois, New Jersey, New York, and Ohio.

Problem

Stores operating without a dedicated or reliable fulfillment team face a persistent verification gap in the current POS workflow:

  • Budtenders can add items manually via the + button and check out without ever scanning a single item — there is no enforcement that physical product was confirmed when the fulfillment dashboard is not part of the workflow.
  • The two-tab workflow (build in POS → validate in fulfillment tab) is a hard training shift for operators migrating from Dutchie who are accustomed to swimlane-based fulfillment.
  • Fulfillment status is not visible in the open POS ticket — there is no in-context signal while an order is being edited.
Key bypass gap
Budtenders can build an order entirely with the + button and check out without any physical product confirmation. This feature closes that gap: when enabled, checkout triggers a scan verification modal that hard-blocks completion until every item has been scanned, with manager override as the only bypass path.

Goals

  • Budtenders complete the full sale — including physical product confirmation — without switching tabs or screens.
  • Checkout is hard-blocked until every item has been scanned at POS, with no bypass outside of a logged manager override.
  • The feature supports three distinct operational models (see Supported Flows) through two config modes (Cashier Scans and Fulfillment First) applied independently per order type.
  • Existing fulfillment infrastructure is reused throughout — FIFO package assignment, package mismatch config, packing receipt format, printer routing, fulfillment dashboard ticket surfacing, and existing block/revert configs — rather than rebuilt. Packing receipt printing from POS is net-new but reuses the existing format and printer routing config.

Non-Goals

  • Does not replace the fulfillment dashboard for BOH-only workflows.
  • Does not change FIFO package assignment logic.
  • Does not introduce a new receipt format.

Scope

In Scope — MVP

  • Save & Exit and Save & Stay bottom bar actions (replace "Save Sale")
  • Order status pill always visible next to Receipt # (Draft → Awaiting Processing → In Process → Packed & Ready)
  • Checkout button triggers scan modal when scanning is required; indicator text shown below button while items remain unverified
  • Scan modal: per-item verification states, All/Scanned/Waiting filter tabs with live counts, progress bar
  • Scan state preserved across modal opens within session (Redux, no new DB column)
  • Auto-fulfilled items pre-checked in modal by product type/subtype config (non-cannabis, deli/bulk)
  • Per-unit barcode scanning (one scan per unit for qty > 1)
  • Wrong product prompt + one-scan add and auto-verify
  • Package mismatch handling (reuse existing config)
  • Cart row "✓ Verified" badge (same badge for POS scan and FF confirmation; no intermediate states)
  • Print Receipt modal (Customer Receipt + Packing Receipt checkboxes; always accessible)
  • Cashier Scans mode: POS scan required at every checkout
  • Fulfillment First mode: reuses existing Packed & Ready block + revert-on-edit configs
  • Config per order type (6 types × Off / Cashier Scans / Fulfillment First); default Off
  • Manager override (PIN, logged)
  • Packing receipt print from POS (net-new; reuses existing format + routing)

Out of Scope — Fast Follow

  • Delta packing receipt (only new/changed items reprinted)
  • Automated order routing to specific printers beyond existing config

Supported Fulfillment Flows

Three distinct operational models are supported. All use the same POS mechanics — they differ in who picks product and whether the fulfillment dashboard is involved.

Config: Fulfillment First. BOH normally processes orders. If Packed & Ready, checkout proceeds without POS scan. If not, cashier must scan before checkout.

Functional Requirements

Save Actions

  • The bottom bar provides two save buttons in place of the old "Save Sale" button: Save & Exit (saves and exits to the customer queue) and Save & Stay (saves and remains on the active sale screen). Both are ghost/outlined style.
  • Saving is how the fulfillment team is notified — the saved ticket surfaces on the FF dashboard automatically. Auto-print config on the FF side determines whether a packing receipt prints in the back. No separate "Send to Fulfillment" action is needed.
  • After either save action: toast appears ("Sale saved."), and the order status pill updates to Awaiting Processing.
  • The same save options (Save & Exit / Save & Stay on Sale) are available in the Current Sale dropdown in the top bar.

Checkout Button

  • Always labeled "Checkout" — the label never changes based on fulfillment state.
  • When items remain unverified and scanning is required, a small indicator appears below the button: "Items require scanning before checkout."
  • When tapped:
    • All items verified (or config does not require scanning): proceed to checkout normally.
    • Scanning required and items unverified: scan modal opens instead.
  • Once all items in the modal are verified, "Verified — Checkout" completes the sale.

Scan Verification Modal

  • Opens when Checkout is tapped and scanning is required. It is a centered overlay — not a full-screen mode change. The cart remains editable while the modal is open.
  • Displays a progress bar (items verified / total) and filter tabs: All / Scanned / Waiting, each with a live item count.
  • Each line shows: product name, package number, quantity, and a validation state indicator (pending circle → checkmark on scan).
  • For qty > 1 lines: each unit requires a separate scan. Progress shown inline ("X of Y scanned").
  • Auto-fulfilled items — store config can exempt certain product types or subtypes from cashier scanning (most commonly non-cannabis items and deli/bulk cannabis weighed at a scale). These items open pre-checked in the modal. Visual treatment: green checkmark, light blue row background (#f3f6fd), blue "Auto-fulfilled · Non-cannabis" or "Auto-fulfilled · Deli/Bulk" label. They count toward progress from open, appear in Scanned and All filter tabs, and never appear in Waiting.
  • Closing the modal (X button) preserves all scan progress for the session. Items already verified remain verified when the modal is reopened. Scan state resets only if items are added or quantities change on the order.
  • Persistence: The POS payment screen is a Redux tab toggle (paymentTabShowing), not a separate page — navigating to payment and back does not destroy the Redux store. Scan state is stored in Redux keyed by ticket ID. sessionStorage keyed by ticket ID is a lightweight fallback for edge cases (browser refresh, device switch). No new DB column or API endpoint required for MVP.
  • "Manager Override" link available for incomplete validation — see Manager Override.

Scan Barcode Type — Design Constraint

The scan verification modal and the FF dashboard both accept any barcode input and mark the item as verified on a match. Neither distinguishes between a product SKU barcode and a package/lot label barcode. Verification confirms "a barcode matching this product was scanned" — not "the exact FIFO-assigned package is physically in hand." This is a known system-wide limitation, not a gap introduced by this feature. See Known Limitations.

Scan-to-add is not treated as verification. The existing POS supports scanning a barcode to add a product to the cart. This is a distinct action from verification — the intent is to add, not confirm, and there is no reliable signal that the physical package was present rather than a shelf tag or display item. Verification always happens explicitly in the scan modal. See Known Limitations for fast-follow recommendation.

There are no invented intermediate states ("Awaiting Scan," "Needs Scan"). The source of verification — POS scan modal or FF team — is not distinguished in the cart. Both carry the same level of certainty and show the same badge. Cart rows update in real time as items are scanned in the modal. Qty controls and the trash icon remain enabled at all times — the cart is never locked.

Print Receipt Modal

  • Tapping "Print Receipt" in the bottom bar opens a modal instead of printing immediately.
  • Two checkbox options: Customer Receipt (checked by default — itemized receipt for the customer) and Packing Receipt (unchecked by default — back-of-house receipt for fulfillment).
  • Print button shows a toast confirming what was printed; Cancel dismisses with no action.
  • Always accessible — not gated on fulfillment state or whether the ticket has been saved.

Fulfillment Status in Open Ticket

Fulfillment status is currently only visible in the saved sale view. This feature requires it to be surfaced in the active open ticket (edit mode) as a status pill alongside the receipt number at all times — including before the ticket is saved. This is a net-new UI change and a prerequisite for Fulfillment First mode.

Cashier Scans mode serves two distinct use cases

No new config keys are required for Fulfillment First. The new POS validation flow is wired as the resolution path when the block fires.

Package Mismatch Config

Reuses the existing fulfillment package mismatch configuration — no new config needed:

  • Auto-update: When a different package of the same product is scanned, the order automatically updates to use the scanned package and the line is marked verified.
  • Confirm before update: A prompt shows the original and scanned package numbers and requires confirmation before updating.

Scanning Logic

FIFO & Package Assignment

When a product is added to the cart (via + button or scan in Build mode), FIFO assigns the oldest eligible package to that line. The packing receipt may print without a lot number if FIFO assignment happens at pick time — this is expected. Validation in the scan modal matches against the specific FIFO-assigned package on the order, not just the product SKU.

Scan Outcomes in Verification Modal

Scan resultSystem behavior
Correct product, correct package, units remaining Unit marked as scanned. Progress updates ("X of Y scanned"). When all units for the line are scanned, line moves to Verified.
Correct product, correct package, line already fully verified No action. Scan acknowledged but does not duplicate verification.
Correct product, different package (FIFO mismatch) Triggers package mismatch handling per existing config — auto-update or confirmation prompt before updating.
Product not on the order Prompt: "This product is not on the order. Would you like to add it?" If confirmed, product is added and auto-verified in one action — no second scan required.
Qty > 1 on a line Each unit requires a separate scan — same as existing fulfillment processing behavior.

Modifying Lines During Verification

  • Reduce quantity: Reduces the required scan count. Already-scanned units in excess of the new qty are discarded.
  • Remove line: Line and any associated scans are discarded. No longer counted toward verification requirement.
  • Partial fulfillment: If a product is unavailable, budtender reduces qty or removes the line, then verifies remaining items. No special partial-fulfillment mode needed.

New Items Added After the Order Is Saved

When a new item is added to an order that has already been saved (and is therefore visible on the FF dashboard), behavior differs by config mode.

Cashier Scans Mode

The new item appears in the cart with no badge. Because Cashier Scans mode rescans all items fresh at checkout, the new item requires no special handling — it is simply part of the full rescan when Checkout is tapped. Saving the order again (Save & Exit or Save & Stay) updates the ticket on the FF dashboard so BOH (if present) sees the new item.

Fulfillment First Mode

Two existing configs handle the happy path:

  1. Adding a new item to a Packed & Ready order triggers the existing "Revert to In Process on edit" config — the order status reverts to In Process in the fulfillment dashboard.
  2. BOH sees the order needs attention, processes the new item, and marks it Packed & Ready again.
  3. Once Packed & Ready, the existing "Block checkout until Packed & Ready" config is satisfied — checkout unblocks with no POS scan required.

If BOH does not re-process the order, it remains In Process (not Packed & Ready) and the Fulfillment First block fires — the scan modal opens at POS. In this case, POS reads fulfilledQuantity per ticket line from the server to pre-populate the modal with what FF already verified, so the cashier only scans items FF has not yet confirmed.

Per-Line Pre-Validation from FF

The existing posper_ticketline.fulfilled_quantity field records how many units of each line FF has processed. It is written only when an order transitions from In Process to Packed & Ready — at that point every line is set to its full ordered quantity. It is not written per-scan; FF scan progress between status transitions is not persisted to the database.

This means fulfilledQuantity is a reliable signal only for lines that have been through at least one PACKED_READY transition:

  • Order was previously Packed & Ready, then pushed back (most common new-item scenario): original lines retain fulfilledQuantity = ordered quantity from the last PACKED_READY. POS shows these as pre-validated. Only the newly added line, which has fulfilledQuantity = 0, requires scanning.
  • Order was never Packed & Ready (still Awaiting Processing or In Process): all lines have fulfilledQuantity = 0. POS cannot distinguish FF progress — cashier scans everything.

POS does not need to write scan results back to the FF dashboard. Once the cashier completes POS validation and the sale is checked out, the ticket moves to Completed — no residual per-line scan state is needed in FF.

What "pre-validated" means in the scan modal
When the Fulfillment First block fires and the scan modal opens, lines where fulfilledQuantity ≥ quantity appear already checked off — the cashier does not need to rescan them. Lines where fulfilledQuantity = 0 are shown as pending and must be scanned. The cashier can see at a glance which item(s) need attention without rescanning everything FF already processed.

Packing Receipt

Printing from POS (Net-New)

Today, packing receipts can only be printed from the fulfillment dashboard. This feature introduces packing receipt printing directly from the POS via the Print Receipt modal — available at any time from the bottom bar, not gated on save or fulfillment state.

For BOH flows, the live FF dashboard order is always the authoritative source — BOH consults the screen, not the receipt. The packing receipt from POS is supplementary and most useful for budtender-picks stores where the receipt serves as a pick list.

Print Receipt Modal

Tapping "Print Receipt" opens a modal with two options: Customer Receipt (checked by default) and Packing Receipt (unchecked by default). Budtender selects which to print and taps Print. A toast confirms what was printed.

When a new item is added after the order is saved, budtenders can reprint the packing receipt from the Print Receipt modal at any time without affecting fulfillment or verification state.

Format & Routing

  • Format: Reuses the existing fulfillment dashboard packing receipt — no new template.
  • Printer routing: Routes to any hardware location configurable in the fulfillment dashboard — no new printer config.

FF Dashboard Badge Gap

When a new item is added to an In Process or Awaiting Processing order, BOH can see it on screen but there is no visual indicator distinguishing it from original items. Out of scope — flagged for the FF team as a follow-up.

Manager Override

  • Available via a "Manager Override" link in the scan verification modal when items remain unverified.
  • Requires entry of a manager PIN.
  • On successful PIN entry, checkout proceeds immediately — scan requirement is bypassed for this transaction.
  • Override is logged with: manager identity, timestamp, ticket ID, count of unverified items, and product names of unverified lines.
  • Override log is accessible to org admins.
  • A persistent indicator on the completed sale record marks that verification was overridden.

Known Limitations

Scan barcode type is not enforced

Neither the POS scan modal nor the FF dashboard distinguishes between a product SKU barcode (identifying the product type) and a package/lot label barcode (identifying the specific physical package assigned to this order via FIFO). Both accept any matching barcode. Verification confirms "a barcode matching this product was scanned" — not "the exact FIFO-assigned package is physically in hand." This is a system-wide limitation that applies equally to both verification sources. Enforcing package-label-only scanning would require barcode type detection infrastructure that does not currently exist.

This limitation is distinct from the scan-to-add concern below. Scanning within the POS scan modal or the FF dashboard is a deliberate verification action — the intent is unambiguous. The barcode type limitation applies to both and does not affect how verification results are surfaced in the cart.

Scan-to-add is not credited as verification (MVP)

The POS supports two ways to add an item to the cart: scanning a barcode (scan-to-add) and tapping the + button on a product card. In MVP, neither method credits the item as pre-verified in the scan modal — all items require an explicit scan at checkout regardless of how they were added.

This creates a redundant double-scan for FOH (front-of-house) stores where budtenders pick items directly from the sales floor and scan them to add to the cart. In this workflow, the budtender physically handled and scanned the item at add time — scanning it again in the verification modal is genuinely redundant.

Why this is not solved in MVP: The POS does not currently track how each item was added. Both scan-to-add (fetchInventoryByBarcode → addTicketline) and + button add (addTicketline) produce identical ticketline records in Redux and on the server — there is no addedByBarcode flag anywhere in the data model. Crediting scan-to-add as pre-verified would require new in-memory Redux tracking keyed by ticketline ID at the moment of add.

Operational context: The double-scan friction is specific to FOH stores running Cashier Scans mode. BOH stores (where a fulfillment team picks and packs items before handing off to the budtender) benefit from explicit verification at checkout because the budtender did not physically handle the items when adding them to the cart. FOH stores using Off config are unaffected. The affected population is FOH stores running Cashier Scans mode — a real but narrower scenario.

Fast-follow recommendation: Track addedByBarcode: true in Redux at the moment a barcode scan resolves to an add (in-memory only, no DB change required). In the scan modal, items flagged addedByBarcode open as pre-verified with a distinct label ("Added by scan") — same visual treatment as auto-fulfilled items. "Simulate: Correct Scan" skips these items. This should be gated on a store-level config option so BOH stores are not affected.

Non-Functional Requirements

  • Scan latency: Scan-to-verification-response must feel instantaneous — target under 300ms from scan input to visual state update in the modal.
  • Offline resilience: If scanner input fails or a product has no barcode, a fallback path must exist — manager override is the minimum acceptable path; a per-line manual "mark as verified" with manager permission is preferred.
  • Audit trail: All manager overrides are logged and retained with the ticket record.
  • Config changes: Changing the validation mode for an order type takes effect on the next new sale. In-progress tickets retain the mode active when the sale was started.
  • No data loss: Opening or closing the scan modal, or re-sending to fulfillment, must not affect ticket line data — products, quantities, prices, discounts, and package assignments are preserved throughout.
