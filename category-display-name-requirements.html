Background

Treez maintains a fixed set of global canonical product categories — Flower, Concentrate, Cartridge, Edible, Pre-Roll, Tincture, Topical, Accessory, and others. These canonical types are Treez-owned and drive purchase limits, tax rules, compliance reporting, and product classification throughout the platform. They cannot be renamed system-wide without downstream risk.

Operators frequently want to display different names for these categories. A dispensary may prefer "Vape" over "Cartridge", "Concentrate" over "Extract", or "Cannabis Flower" over "Flower" to better match their brand voice and how their customers talk. Today there is no mechanism to do this — category names are locked to the Treez canonical.

Category Display Names introduces a lightweight rename layer: org-specific display name overrides on top of the global canonical layer. Products retain their canonical category assignment and all the compliance metadata that comes with it. Only the label shown in the UI changes. This feature is intentionally simpler than Custom Subcategories — operators do not create new categories, reassign products, or manage a separate taxonomy. They rename only.

Core Concepts

Global Canonical Categories

Treez-owned. Fixed set. Cannot be renamed or removed by orgs. Drive all compliance, limits, and classification logic.

  • Purchase limit evaluation
  • Tax rule application
  • Metrc compliance reporting
  • Type icon mapping
  • Collection rule evaluation

Org Category Display Names

Per-org label overrides. One row per category an org has renamed. No row = falls back to canonical name.

  • Org-scoped — no MSO inheritance
  • Rename only — no new categories created
  • Does not affect any evaluation logic
  • Can be cleared to restore canonical label

Resolved categoryDisplayName — Single Field, Server-Side

All surfaces read from one resolved field. No fallback logic needed on the client.

  • Resolution: categoryDisplayName = customDisplayName ?? canonicalType
  • Resolved server-side in PMS and PMRS — callers receive the final label
  • Stamped on ticket lines at time of sale — receipts reflect the name active when the sale occurred
  • Canonical type field is always present and unchanged alongside categoryDisplayName

Design Decisions

Rename only — no create, no delete of categories

The full set of canonical categories is always present in the management UI. Operators edit display names on top of existing categories. They cannot add new categories or remove existing ones. This is intentional — category taxonomy is controlled by Treez.

Org-scoped, no MSO inheritance

Each location manages its own category display names independently. If an MSO wants consistent naming across locations, each location must set the same override. MSO-level inheritance is not supported and is out of scope.

All evaluation logic stays on canonical type

Purchase limits, discount conditions, collection rules, tax rules, compliance reporting — all evaluate against the canonical type. Display name is a label change only. There are no behavior changes to any rule or limit system.

Type icons are unchanged

Type icons (Flower icon, Concentrate icon, etc.) are keyed on canonical type and are not configurable by orgs. Wherever an icon appears alongside a category label, the icon stays canonical and only the text label switches to the display name.

Search matches both canonical name and display name

An operator who has renamed "Cartridge" to "Vape" will search by "Vape" — so search must match against categoryDisplayName. But staff accustomed to the old name, or third-party integrations, may still use "Cartridge" — so the canonical name must also remain searchable. Both must work.

Ticket line stamping at time of sale

When a sale is completed, the resolved categoryDisplayName active at that moment is stamped onto the ticket line. Receipts always show the name that was in effect at the time of sale. If an operator later renames a category, historical receipts are not affected.

/onlinemenu excluded

The legacy eCommerce online menu (/onlinemenu) is out of scope. Category display names are not surfaced there. Only the current eCommerce product surfaces are in scope.

Management UI MVP

Feature flag: Catalog Management - Category Display Names gates all management surfaces. The underlying schema and resolved API fields ship to all orgs; the management UI and display name override behavior are flag-gated per org.

Category Display Names lives in catalog-management-mfe, as a new section within catalog management. The management view is a fixed list — all canonical Treez categories are always present. Operators rename any of them. There is nothing to create or delete at the category level.

Category Display Names List
  • All canonical Treez product categories are listed — no filtering or pagination required given the small fixed set.
  • Each row shows the type icon (keyed on canonical, not editable), the canonical type name (shown as a reference label), and the current custom display name if one has been set.
  • Rows without a display name override show a placeholder or empty state.
  • The list is not orderable — canonical ordering applies.
Setting a Display Name
  • Each row has an inline text input for the display name. The operator types the desired name and saves.
  • Save feedback is visible — inline confirmation or a toast.
  • Display name is free text. No uniqueness constraint across rows — two categories could share the same display name if the operator intends it (though this is unlikely).
  • Empty string or clearing the field resets the category to its canonical name.
Resetting to Canonical
  • A clear or reset option per row removes the display name override and reverts the category to its canonical label everywhere in the app.
  • No confirmation required — the operator can set the name again immediately if they change their mind.

Data Model & Resolution

Storage (PMS)

A new table in PMS stores per-org overrides. Only categories that have been renamed need a row — absent rows fall back to the canonical name.

org_category_display_name
  org_id          UUID      -- FK to org
  canonical_type  VARCHAR   -- e.g. "FLOWER", "CARTRIDGE", "CONCENTRATE"
  display_name    VARCHAR   -- org's chosen label
  PRIMARY KEY (org_id, canonical_type)

Resolution Pattern

Resolution is always server-side. Clients receive one field and do no fallback logic.

categoryDisplayName = UPPER(COALESCE(NULLIF(customDisplayName, ''), canonicalType))

This resolved field is exposed by:

  • PMS — on Product GET and list responses alongside the existing type field
  • PMRS — as a stored column (ingested from PMS events) and exposed as a virtual resolved field on /st/v1/products
  • IS — indexed in Elasticsearch and stamped on ticket lines at sale time

PMRS — Search & Filter

PMRS stores categoryDisplayName as a column and supports querying in two ways:

  • Filter by canonical type — used by chips and programmatic filters for stability. Chip tap sends canonical type, not display name string.
  • Filter by display name — used by free-text search. Matching against both categoryDisplayName and canonical type ensures the old and new name both work.
  • Distinct endpoint — returns {canonical, categoryDisplayName} pairs so UI can render the display label while holding the canonical value as the filter key.
  • An expression index on categoryDisplayName covers filter performance.

IS — Elasticsearch & Ticket Line Stamping

IS indexes categoryDisplayName on its Elasticsearch product document. Type-based search queries match against both canonical type and categoryDisplayName. The category list endpoint used by the POS to populate filter chips returns {canonical, categoryDisplayName} pairs.

At sale time, the resolved categoryDisplayName value is stamped onto the ticket line — the same pattern used for subcategory display name stamping. Historical ticket lines are not backfilled.

SellTreez — Front of House

All FOH surfaces read from the resolved categoryDisplayName field. No client-side fallback logic is required — the field always carries the right label.

Note: Category (type) appears in significantly more SellTreez surfaces than subcategory. Category is a primary navigation axis in the POS — it drives the top-level filter chips and appears on product cards, line items, and throughout inventory and reporting. Each surface below requires explicit attention.
POS Type Filter Chips
  • The type filter chips at the top of the POS product menu show categoryDisplayName as the text label.
  • Type icons are unchanged — keyed on canonical type.
  • The filter value sent to search remains the canonical type, not the display name string. Chip selection is stable across display name changes.
  • Chip options are populated from the IS category list endpoint, which returns {canonical, categoryDisplayName} pairs.
Free-Text Product Search
  • Free-text search in the POS matches against categoryDisplayName in addition to canonical type.
  • Searching for either the old canonical name or the new display name returns matching products — backward compatibility is preserved for staff accustomed to old names.
Product Cards
  • Category labels shown on product cards in the POS grid display categoryDisplayName.
Product Detail Modal / Drawer
  • The category/type field in the product detail modal shows categoryDisplayName.
Cart and Ticket Line Items
  • Category shown on cart line items displays categoryDisplayName.
Receipts (Print, Email, SMS)
  • All receipt types display the categoryDisplayName where category is shown.
  • The display name is read from the value stamped on the ticket line at the time of sale — not a live lookup. Receipts reflect the name that was active when the transaction occurred.
Product List Page
  • The category column in the product list shows categoryDisplayName.
  • Applies to both the read-only product list and the product list within purchase invoices in Purchasing.
Product Groups — Legacy Discount Management
  • Category type icons and labels in the Product Groups rule builder and member list show categoryDisplayName as the text label. Icons are unchanged.
  • Category filter dropdowns used when defining a Product Group rule show categoryDisplayName as the option label.
  • Rule evaluation and stored rule values remain canonical types — this is a display-only change.
MSO Product Collections
  • Category type icons and labels in MSO Product Collection rule builders and member lists show categoryDisplayName as the text label. Icons are unchanged.
  • Collection membership evaluation and stored rule values remain canonical types — display-only change.
Purchase Limits
  • Wherever a category label appears in the purchase limits UI — limit configuration, limit enforcement display, and staff-facing limit summaries — show categoryDisplayName.
  • Purchase limit evaluation is unchanged — all enforcement logic operates on canonical type.
Discount Conditions
  • Category type dropdowns in the discount condition builder show categoryDisplayName as the visible label.
  • Stored condition values and discount evaluation logic remain canonical types.

SellTreez — Other Teams

All other-team surfaces read from the resolved categoryDisplayName field. The canonical type field remains available and unchanged for any surface that needs both.

Inventory Management and Count/Audit (Inventory & Count Treez)
  • Category shown in inventory management views and count/audit workflows displays categoryDisplayName.
In-App Reporting
  • In-app reports that display category (Product Summary, Product Log, Discount Log, Inventory Log, Inventory Valuation) show categoryDisplayName in the category column.
  • Category-based search and filter in reports matches against categoryDisplayName — operators filter by the name they see in the app.
  • Sales CSV exports (Product, Discount, Tax): category/type column shows categoryDisplayName; a separate "Treez Global Category" column is appended at the end with the canonical type for audit and compliance. Same pattern as subcategory CSV exports.
  • Inventory CSV exports (Log, Valuation, Invoice): category/type column shows categoryDisplayName only — no additional column.
  • Historical report data shows the canonical type name — no backfill.
Label Templates
  • Label templates that include a category/type field reflect categoryDisplayName where one exists, falling back to the canonical name.

External APIs

Category display name fields are additive — the existing type / product_type fields on all external APIs are unchanged. No breaking changes.

External Product API + Webhook
  • New field category_display_name added immediately after the existing type field in the product API response.
  • Same field included in the product webhook payload.
  • Value is the resolved display name — custom if set, canonical fallback if not.
External Ticket API (Line Items) + Webhook
  • New field product_category_display_name added immediately after product_type on each ticket line item in the REST response.
  • Same field included in the ticket webhook payload.
  • Value is the display name stamped on the ticket line at time of sale.
External Stock / Inventory API
  • New field category_display_name added immediately after product_type in the stock/inventory API response.
  • Value is the resolved display name — custom if set, canonical fallback if not.

Out of Scope Not included

  • /onlinemenu (legacy eCommerce) — Category display names are not surfaced in the legacy online menu.
  • MSO category name inheritance — Each location manages its own display names independently. No parent-org override that cascades to child locations.
  • Creating new categories — The canonical category list is fixed. Operators can only rename, not extend it.
  • Reordering categories — The order of canonical categories in any listing is not configurable by orgs.
  • Category icon customization — Type icons are keyed on canonical type and are not configurable.
  • Sorting by display name — PMRS returns a 422 for sort by this field; sorting is not supported. Filtering and distinct are supported.
  • Historical ticket line backfill — Ticket lines created before this feature ships retain only the canonical type. No backfill.
  • Retail Analytics / Reporting team reports — Out of scope for MVP; reporting team handles their data store separately.

vs. Custom Subcategories

Category Display Names is intentionally simpler than the Custom Subcategories feature. It covers a narrower user need — rename only — and avoids the complexity of a full org-specific taxonomy layer.

Dimension Custom Subcategories Category Display Names
New entities created by org Yes — org creates custom subcategory entries No — rename only on fixed canonical list
Product assignment Products are assigned to a custom subcategory (new FK on product) No change — products stay assigned to canonical category
Reassignment flow Yes — bulk move products between subcategories (fast follow) Not applicable
Delete flow Yes — delete custom when 0 products assigned Not applicable — clearing a display name just resets to canonical
Management UI complexity High — CRUD with activate/deactivate, shadowing, reassign modal Low — fixed list with inline rename field, reset option
Product FK changes Yes — nullable customSubCategoryId added to product No FK changes on product
Resolved field subCategoryDisplayName categoryDisplayName
Number of canonicals affected Subcategory level (~100+) Category level (~10)
POS surface prominence Subcategory chips (secondary filter) Type chips (primary navigation) — higher visibility
Evaluation logic changes None — evaluation stays on canonical None — evaluation stays on canonical

Feature Flag

Flag name: Catalog Management - Category Display Names
Managed in org-management service, same pattern as Catalog Management - Custom Subcategory Management.

The feature flag gates:

  • The Category Display Names management view in catalog-management-mfe
  • The ability to set, update, or delete display name overrides via the management API

The feature flag does not gate:

  • The underlying schema (org_category_display_name table)
  • The categoryDisplayName field on PMS, PMRS, and IS responses — these resolve to canonical for all orgs until an override is set, so they are safe to ship universally
  • The new fields on external APIs — these are additive and always present, returning canonical name for orgs without overrides
